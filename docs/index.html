Blackwall Wiki

A self-hosted anti-spam and moderation platform for Discord and Twitch, combining real-time bots for spam detection with a web dashboard for server and channel configuration — all backed by Discord and Twitch OAuth2 authentication. Includes bot allowlist protection against automated attacks that disguise themselves as bot accounts.

.NET 10 PostgreSQL 17 Redis 7 Blazor Server Docker
📝 Get Started ⚙ .env Generator 🔗 GitHub

Features

⚡ Real-time Spam Detection

Sliding-window rate limiting, sliding-window duplicate detection with cross-channel support, mention flooding, invite link blocking, and suspicious link filtering — all in real time.

🛡 Content Guard

Banned word filtering with Levenshtein fuzzy matching and leetspeak normalisation, Zalgo text blocking, copypasta hash detection, and invisible character scrubbing.

🔗 Link Blocking

AdGuard-format blacklist support with custom domains, whitelist mode, and Google Safe Browsing real-time threat checks via a locally synced Global Cache.

🚨 Anti-Raid

Velocity-based join detection that automatically pauses invites when a raid threshold is reached, with configurable cooldown.

🤖 Account Scoring

Evaluates new members on join based on account age, profile picture, and username patterns; assigns a threat score with optional auto-timeout.

🪜 NetWatchSnare

Trap channels that automatically punish users who post in them, with configurable actions per trap.

🔒 Lockdown

Instantly deny send permissions for @everyone across all channels, manually or automatically on infraction.

🛑 Ban Management

Share, sync, and import bans across Blackwall-managed servers with auto-sync support.

📝 Message Audit

Records deleted messages and infraction events with configurable retention for review in the dashboard.

✅ Bot Allowlist

Only trusted bots bypass spam detection. All other bot-flagged accounts — including attack tools disguised as bots — are scanned.

🧪 Dry Run Mode

Test detection rules without taking action against users. Detections are logged only.

🌐 Per-guild / Per-channel Configuration

Each Discord server and Twitch channel gets its own spam thresholds, module toggles, and actions managed through the web dashboard.

🔑 Discord & Twitch OAuth2 Login

Users authenticate via Discord or Twitch. Accounts can be linked, unlinked, and merged. JWT tokens are issued for API and Web access.

🔄 Guild Permission Sync

A background service periodically synchronises guild manager permissions from Discord.

🔄 Twitch Ban Sync

A background service synchronises shared ban lists across Blackwall-managed Twitch channels.

💻 Web Dashboard

Blazor Server UI for guild and channel owners to configure spam rules visually.

🧪 Third-Party Modules

Extend detection capabilities with community-built .NET modules loaded dynamically from Git repositories. Supports Discord, Twitch, or both platforms simultaneously.

Architecture

Blackwall is a .NET 10 solution split into the following projects:

ProjectDescription
Blackwall.CoreShared entities, DTOs, and configuration models
Blackwall.InfrastructurePostgreSQL persistence (EF Core) and Redis caching
Blackwall.Bot.DiscordDiscord gateway client — spam detection, guild events, background sync
Blackwall.Bot.TwitchTwitch IRC client — spam detection, channel moderation, module evaluation
Blackwall.ApiASP.NET Core Web API — OAuth flows, JWT auth, guild/channel management endpoints
Blackwall.WebBlazor Server dashboard — authenticates against the API
Blackwall.Modules.AbstractionsModule SDK — interfaces, manifests, and data structures for third-party modules
Blackwall.Modules.RuntimeShared runtime — module loading, evaluation, and build helpers
How it fits together The API hosts the bot (as a hosted service), serves REST endpoints for the dashboard, and handles OAuth. The Web project is a Blazor Server app that calls the API. Both share the same JWT secret for authentication.

Prerequisites

  • .NET 10 SDK — Download
  • PostgreSQL 17+ — for persistent data storage
  • Redis 7+ — for caching
  • A Discord application with bot and OAuth2 credentials — create one at the Discord Developer Portal
  • A Twitch application (optional) for Twitch login support — create one at the Twitch Developer Console
Docker users If you're using Docker Compose, you don't need to install .NET, PostgreSQL, or Redis manually — they're all containerised.

Installation

1

Clone the repository

git clone https://github.com/pedrocavaleiro/Blackwall.git
cd Blackwall
2

Configure environment variables

Copy the example file and fill in your values:

cp .env.example .env

Edit .env with your configuration. See the Environment Variables section for a full reference, or use the .env Generator to interactively build your file.

Quick start Use the .env Generator tool — it provides one-click key generation for JWT secrets and AES encryption keys, plus inline help for every field.
3

Configure appsettings.json

In src/Blackwall.Api/appsettings.json, set the AllowedUsers array to the Discord user IDs permitted to register when APP__PRIVATE_INSTANCE=true:

"AllowedUsers": ["123456789012345678", "987654321098765432"]
Instance owner The owner (set via APP__INSTANCE_OWNER) is always allowed to register even if not listed in AllowedUsers.
4

Run Entity Framework migrations

Apply the database schema before starting the API:

dotnet ef database update --project src/Blackwall.Infrastructure --startup-project src/Blackwall.Api
Docker Compose Migrations are applied automatically on first run when using Docker Compose.
5

Start the application

Choose your deployment method — see the Deployment section below for detailed options.

Deployment

Blackwall supports three deployment methods. Choose the one that fits your infrastructure:

🐳 Docker Compose

Quickest setup. Everything containerised — PostgreSQL, Redis, API, Web, and Nginx.

🖩 Proxmox LXC

Provision a Debian 13 LXC container with automated setup scripts and systemd services.

💻 Bare Metal / VM

Install prerequisites directly and run natively. Full control for development or custom setups.

Deployment: Docker Compose

The quickest way to get everything running. Requires only Docker and Docker Compose.

Steps

  1. Create your .env file (use the .env Generator).
  2. Set POSTGRES_PASSWORD in your environment or .env for the Postgres container.
  3. Run: 
    docker compose up --build
  4. The stack will be available on port 80 via the Nginx reverse proxy.

Nginx routing

  • /api/ → API container (port 8080)
  • / → Web container (port 8080, with WebSocket upgrade support for Blazor)
Docker internals Inside Docker, the API and Web run on port 8080. Nginx maps port 80 externally. The Web container calls the API at http://api:8080 using Docker's internal DNS.

Deployment: Proxmox LXC

The infra/lxc/ directory contains scripts for provisioning a Debian 13 (Trixie) LXC container and deploying published builds.

Step 1: Provision the container

Run setup.sh as root inside the LXC. It installs:

  • .NET 10 ASP.NET Core Runtime
  • PostgreSQL 17
  • Redis
  • Nginx
  • Creates the blackwall system user and directories at /opt/blackwall
  • Creates the PostgreSQL database and user (prints credentials)
  • Installs systemd services (blackwall-api, blackwall-web)
  • Configures Nginx as a reverse proxy
scp -r infra/lxc/ root@<lxc-ip>:/tmp/blackwall-setup
ssh root@<lxc-ip> "bash /tmp/blackwall-setup/setup.sh"
Save the credentials The setup script prints the PostgreSQL connection string. Save it — you'll need it in your .env.

Step 2: Place your .env

Place your .env at /opt/blackwall/.env on the LXC:

chown blackwall:blackwall /opt/blackwall/.env
chmod 640 /opt/blackwall/.env

Step 3: Deploy

From your dev machine, publish and upload both projects:

./infra/lxc/deploy.sh <lxc-ip>

This builds Release artifacts, uploads them via rsync, fixes ownership, and restarts the systemd services.

Windows deploy script

A PowerShell equivalent is also available:

.\infra\lxc\deploy.ps1 -LxcIp <lxc-ip>

Preserving config across deploys

The deploy script excludes .env and appsettings.Production.json from rsync, so user customizations are never overwritten. appsettings.json (base defaults) is always synced, meaning structural changes from the repo propagate automatically.

To override settings locally, create appsettings.Production.json in /opt/blackwall/api/ and/or /opt/blackwall/web/ with only the keys you want to change.

Account Linking & Multi-Provider Login

Blackwall supports login via both Discord and Twitch. Users can link both providers to a single account, switch their display name between providers, and unlink providers when no longer needed.

Login Flow

When both Discord and Twitch are configured, the login modal shows two buttons: Discord and Twitch. Users choose their provider at login. If only Discord is configured (Twitch credentials are blank), only the Discord button is shown.

Account Linking

After logging in with one provider, users can link the other provider from the Accounts modal in the navigation bar. The flow:

  1. User clicks ACCOUNTS in the nav bar.
  2. The Accounts modal shows linked providers and a LINK button for unlinked providers.
  3. Clicking LINK initiates the OAuth flow for the missing provider. The linkTo user ID is stored in Redis alongside the OAuth state.
  4. On callback, if a linkTo value is found, the provider is linked to the existing account instead of creating a new one.
  5. If the OAuth provider's user ID already exists on a different account, the two accounts are merged — guild ownership, manager roles, and tokens are consolidated into the primary account.

Account Merging

When a user who already has an account logs in with a second provider and a different account already exists for that provider's user ID, Blackwall merges the two accounts:

  • Guild ownership and manager roles from the duplicate account are transferred to the primary account.
  • Missing provider tokens (Discord or Twitch) are copied from the duplicate to the primary.
  • The duplicate account is deleted.
  • The display name provider is set automatically if the primary account didn't have one.

Unlinking

Users can unlink a provider from the Accounts modal. When unlinking Discord:

  • If the user owns guilds with no other managers, those guilds are orphaned — the bot leaves them and the guild instances are deactivated.
  • A warning is shown before unlinking if orphan guilds would be created.
  • The display name provider is automatically switched to Twitch if available.

Unlinking Twitch simply removes the Twitch credentials and switches the display name provider to Discord if available.

Display Name Selection

When both providers are linked, users can choose which provider's display name to use in the dashboard. The selected name appears in the navigation bar and is updated live without a page reload.

Link Accounts Warning Banner

When a user has only one provider linked, a banner appears below the header suggesting they link the other provider. The banner can be dismissed permanently — the dismissal is stored server-side on the user entity, so it persists across devices and sessions.

Twitch setup To enable Twitch login, set TWITCH__CLIENT_ID, TWITCH__CLIENT_SECRET, and TWITCH__REDIRECT_URI in your .env. The redirect URI must be https://your-domain.tld/api/auth/twitch/callback and must match the OAuth Redirect URL configured in the Twitch Developer Console.

Configurable Actions

For medium and high risk accounts, you can independently enable auto-timeout:

  • Auto-timeout medium risk — automatically places medium-risk users in a timeout on join
  • Auto-timeout high risk — automatically places high-risk users in a timeout on join

If auto-timeout is disabled for a given level, moderators are alerted only and can manually decide whether to intervene. The timeout duration is configurable (default: 10 minutes).

Alerts All alerts are sent to the configured audit log channel as an embed containing the user, their score, account age, the specific risk factors that contributed, and the action taken.

Content Guard

Content Guard is the advanced toxicity and evasion filtering layer. It goes beyond simple keyword matching by detecting intentional obfuscation, Unicode abuse, and coordinated copypasta attacks. Each algorithm can be toggled independently — if all algorithms are disabled, only the basic banned word list is enforced. Disabling Content Guard entirely turns off all filtering including the banned word list.

Algorithms

AlgorithmSettingsDescription
Levenshtein fuzzy matchingEdit distance threshold (1–5)Uses fuzzy string matching to catch intentional misspellings and leetspeak (e.g. replacing i with 1 or e with 3). Tokens within the edit distance threshold of a banned word are flagged. Leetspeak normalisation is always applied before comparison.
Invisible character scrubbing—Strips zero-width spaces, zero-width joiners, word joiners, BOM, and left/right-to-right marks from messages before evaluating banned words. Prevents bypass via invisible Unicode injection.
Zalgo / clutter blockingMax consecutive combining marks (1–10)Blocks messages containing excessive Unicode combining characters (Zalgo text) that lag mobile clients and visually destroy the chat window.
Copypasta hashingMin length (50–5000), distinct user threshold (≥2), time window (10–3600 s)Calculates a SHA-256 hash of incoming large text blocks. If the same block is posted by multiple distinct users within the time window, all matching messages are flagged. Targets coordinated text spam during live streams.

Banned Words

A per-guild editable list of banned words. Words are matched case-insensitively after leetspeak normalisation. Add individual words or short phrases (spaces are preserved). When fuzzy matching is enabled, close variations of banned words are also caught.

How leetspeak normalisation works Before any comparison, the message text is normalised: 1→i, 3→e, 4→a, 0→o, 5→s, 7→t, and @→a. This means h3ll0 is matched as hello. The normalised text is then compared against the banned word list and, if fuzzy matching is enabled, against nearby edit distances.

Module Actions

Content Guard has its own configurable action (delete only, timeout, kick, or ban), timeout duration, message delete days (when banning), and auto-lockdown toggle — independent from other detection filters.

NetWatchSnare

NetWatchSnare provides trap channels — channels where any user who posts in them is automatically punished. This is useful for channels that should never receive messages, such as announcement channels where only admins post, or decoy channels designed to catch bots and spammers scanning the channel list.

How It Works

  • Each trap channel is configured individually with its own action, timeout duration, and message delete days.
  • When a user sends a message in a trap channel, the message is immediately deleted and the configured action is applied.
  • Trap channels are checked early in the message processing pipeline — before any other spam detection runs.
  • The action is applied even if the guild is in dry-run mode (the trap always fires).
Always enforces Unlike other modules that respect the global dry-run setting, NetWatchSnare traps always apply their configured action. This is by design — a trap that doesn't punish defeats its purpose. If you need to test without consequences, remove the trap channel first.

Configuration

Each trap channel is configured independently:

SettingDescription
ChannelThe Discord channel to monitor. Any message sent in this channel by a non-allowed user triggers the trap.
ActionWhat happens to the user: Delete only, Timeout, Kick, or Ban.
Timeout durationHow long the user is timed out (when action is Timeout). Minimum: 1 minute.
Message delete daysDays of message history to prune when banning (0–7). Only shown when action is Ban.
Typical use cases Announcement channels where only admins should post, read-only instruction channels, decoy channels placed to catch automated spam bots that scan the channel list, and channels that should only contain bot messages.

Modules

Blackwall is organised into independent modules, each configurable per Discord guild or per Twitch channel through the dashboard. Every module can be toggled on or off, and most support configurable actions (delete only, timeout, kick, or ban) with optional auto-lockdown. Modules stack — a single message can trigger multiple filters simultaneously.

General

Master controls for barrier activation, enforcement mode, and bot allowlist.

SettingDescription
Enable barrierWhen off, the bot will not process any messages in this server. All other modules are effectively disabled.
Dry runDetections are logged but no action is taken against the user. Useful for testing configuration changes before enforcing them.
LockdownInstantly denies Send Messages, Send Messages in Threads, and Create Public Threads for @everyone in every text channel and category via channel-specific permission overwrites. Higher-tier roles are unaffected. Can be toggled from the dashboard or via the /lockdown and /unlock slash commands in Discord.
Allowed botsA per-guild list of bot accounts that are skipped by the spam detection pipeline. The Blackwall bot itself is always exempt automatically. All other bot-flagged accounts — including automated attacks that disguise themselves as bots — are processed through the full spam detection pipeline. Add only bots you trust (moderation bots, logging bots, music bots, etc.) by entering their Discord ID and an optional name. Webhooks are always skipped regardless of this list.
Why allowlist bots? Some attack tools send messages through gateways that cause Discord to flag the account as a bot (IsBot=true). Without an allowlist, these attacks would bypass spam detection entirely. The allowlist inverts this: only explicitly trusted bots are skipped, and everything else flagged as a bot is still scanned.

Detection Matrix

Controls how the barrier detects and neutralizes spam, duplicate floods, and mass-mention attacks. Each filter runs independently and stacks with the infraction action set in General.

FilterSettingsDescription
Rate limitingWindow (seconds), max messages per windowCounts messages from a single user using a true sliding window. The next message after the limit triggers an infraction. Entries older than the window are continuously evicted, so spacing messages out does not reset the counter.
Duplicate detectionThreshold, window (seconds), cross-channel toggleTracks identical message hashes per user using a true sliding window. When the threshold is reached within the window, the filter trips. Cross-channel mode counts duplicates across different channels; per-channel mode only counts within the same channel. Set threshold to 0 to disable.
Mention limitMax mentions per messageFlags messages that exceed the configured combined user, role, and @everyone/@here mention count as mass-ping spam.

Each detection filter has its own configurable action (delete only, timeout, kick, or ban), timeout duration (when applicable), message delete days (when banning, up to 7 days), and auto-lockdown toggle.

Real-time threat check powered by a locally synchronized Global Cache from Google Safe Browsing. All URL checks are resolved locally against the synced cache — no URL data or hash prefixes are ever sent to Google. Only available when SAFE_BROWSING__ENABLED=true is set server-side.

AdGuard-format blacklist URLs. Domains from these lists are downloaded, merged, and cached in Redis. Refreshed daily. You can add from defaults (Blocklist Project lists), add custom URLs, or trigger a manual refresh. Hidden when whitelist mode is active.

Individual domains to block in addition to the blacklists above. Subdomains are matched automatically. In whitelist mode, this list becomes the Allowed Domains list — only links to these domains are allowed and all other external links are blocked.

Content Guard

Advanced toxicity and evasion filtering. Each algorithm can be toggled independently. If all algorithms are disabled, only the basic banned word list is enforced. Disable Content Guard entirely to turn off all filtering including the banned word list.

Custom Modules (3rd-Party)

Blackwall supports loading external modules at runtime. A custom module is a .NET 10 assembly that implements the IBlackwallModule interface and is packaged as a Git repository with a manifest file. Modules are cloned, built, and installed per guild or per Twitch channel through the dashboard or API, then loaded into a collectible AssemblyLoadContext so they can be hot-reloaded without restarting the bot. A module can target Discord, Twitch, or both platforms simultaneously.

How it works When a message arrives, the bot fetches all enabled module installations for the guild or Twitch channel from cache, loads each module's assembly (if not already cached), calls EvaluateAsync with a 5-second timeout, and collects verdicts. Each verdict is mapped to an infraction action and applied alongside the built-in filters. Modules stack with each other and with all built-in detection.

Installation Controls

Instance administrators can control third-party module installation via two environment variables:

  • MODULES__ALLOW_THIRD_PARTY — master switch. When false, all module installation is disabled (both catalog and Git URL). The web dashboard shows a “disabled by administrator” message instead of the install UI.
  • MODULES__CATALOG_ONLY — when ALLOW_THIRD_PARTY is true, setting this to true restricts installations to modules listed in the curated catalog only. The manual Git URL input is hidden from the dashboard, and the API rejects Git URLs not present in the registry.

Module Lifecycle

1

Install

The dashboard or API provides a Git URL. Blackwall clones the repository, reads blackwall-module.json from the root, validates the manifest, runs dotnet build -c Release in the src/ directory, and copies the output DLL (plus .deps.json and .runtimeconfig.json if present) into modules/<name>/<version>/. A database record is created with default settings derived from the manifest's settings schema.

2

Load

On the first message after installation, the module assembly is loaded into a collectible AssemblyLoadContext. Blackwall scans the assembly for a type implementing IBlackwallModule, instantiates it, and calls InitializeAsync with the stored settings. The loaded instance is cached by name:version key for subsequent messages.

3

Evaluate

For each incoming message, EvaluateAsync is called with a ModuleMessageContext containing the message content, author, channel, attachments, and embeds. The module returns a ModuleVerdict if the message violates its rules, or null to pass. A 5-second timeout is enforced per module.

4

Update / Uninstall

Settings can be updated at any time through the dashboard — the module's UpdateSettingsAsync is called live without reloading the assembly. Updating a module re-clones the repository, rebuilds, and swaps the DLL. The old AssemblyLoadContext is unloaded so the new version loads on the next message. Uninstalling removes the database record and unloads the assembly.

Repository Structure

A module repository must have the following layout:

my-module/
├── blackwall-module.json          # Manifest (required, root)
└── src/                           # Project directory (required)
    ├── MyModule.csproj            # .NET 10 project targeting net10.0
    ├── MyModule.cs                 # IBlackwallModule implementation
    └── Blackwall.Modules.Abstractions.dll  # Reference assembly
Build requirements The src/ directory must contain exactly one .csproj file targeting net10.0. The build is run with dotnet build -c Release in an isolated environment with a temporary NuGet cache. The Blackwall.Modules.Abstractions.dll reference assembly must be committed in src/ alongside the project file.

Assembly isolation At runtime, any assembly whose name starts with Blackwall is resolved from the host (not the module's directory). This means the module always uses the host's Blackwall.Modules.Abstractions types at runtime, ensuring interface compatibility. The .dll in src/ is only needed for compilation.

Complete Example

Here is a minimal module that flags messages containing more than a configurable number of emoji:

using System.Text.RegularExpressions;
using Blackwall.Modules.Abstractions;

namespace MyModule;

public sealed partial class EmojiSpamModule : IBlackwallModule
{
    private static readonly Regex UnicodeEmojiRegex = CreateUnicodeEmojiRegex();
    private static readonly Regex CustomEmojiRegex = CreateCustomEmojiRegex();

    private int _maxEmojiCount = 5;
    private bool _countCustomEmoji = true;
    private ModuleAction _action = ModuleAction.DeleteOnly;
    private int _timeoutMinutes = 5;
    private int _messageDeleteDays = 0;
    private bool _autoLockdown = false;

    public string Name => "emoji-spam";
    public string Version => "1.0.0";

    public Task InitializeAsync(ModuleSettings settings, CancellationToken ct)
    {
        _maxEmojiCount = settings.GetInt32("maxEmojiCount") ?? 5;
        _countCustomEmoji = settings.GetBoolean("countCustomEmoji") ?? true;
        _timeoutMinutes = settings.GetInt32("__timeoutMinutes") ?? 5;
        _messageDeleteDays = settings.GetInt32("__messageDeleteDays") ?? 0;
        _autoLockdown = settings.GetBoolean("__autoLockdown") ?? false;

        var actionStr = settings.Get("__action");
        if (!string.IsNullOrEmpty(actionStr)
            && Enum.TryParse<ModuleAction>(actionStr, true, out var action))
            _action = action;

        return Task.CompletedTask;
    }

    public Task<ModuleVerdict?> EvaluateAsync(ModuleMessageContext context, CancellationToken ct)
    {
        if (context.Content is null)
            return Task.FromResult<ModuleVerdict?>(null);

        var count = UnicodeEmojiRegex.Matches(context.Content).Count;

        if (_countCustomEmoji)
            count += CustomEmojiRegex.Matches(context.Content).Count;

        if (count > _maxEmojiCount)
        {
            return Task.FromResult<ModuleVerdict?>(new ModuleVerdict(
                ViolationType: "emoji-spam",
                Action: _action,
                TimeoutMinutes: _timeoutMinutes,
                DeleteDays: _messageDeleteDays,
                AutoLockdown: _autoLockdown,
                Reason: $"Message contains {count} emoji (limit: {_maxEmojiCount})"
            ));
        }

        return Task.FromResult<ModuleVerdict?>(null);
    }

    public Task UpdateSettingsAsync(ModuleSettings settings, CancellationToken ct)
        => InitializeAsync(settings, ct);

    // Use surrogate-pair ranges for supplementary-plane emoji (U+1F000-U+1FAFF)
    [GeneratedRegex(@"(?:\uD83C[\uDC00-\uDFFF]|\uD83D[\uDC00-\uDFFF]|\uD83E[\uDC00-\uDEFF])|[\u2600-\u27BF\uFE0F]", RegexOptions.CultureInvariant)]
    private static partial Regex CreateUnicodeEmojiRegex();

    [GeneratedRegex(@"<a?:\w+:\d+>", RegexOptions.CultureInvariant)]
    private static partial Regex CreateCustomEmojiRegex();
}

Installing a Custom Module

Modules are installed per guild or per Twitch channel through the dashboard's Modules tab or via the API:

  • Dashboard (Discord) — Navigate to your guild → Modules → Install, and paste the HTTPS Git URL of your module repository.
  • Dashboard (Twitch) — Navigate to your channel → Modules → Install, and paste the HTTPS Git URL of your module repository.
  • API (Discord) — POST /guilds/{discordGuildId}/modules/install with a JSON body { "gitUrl": "https://github.com/..." }.
  • API (Twitch) — POST /twitchchannels/{twitchUserId}/modules/install with a JSON body { "gitUrl": "https://github.com/..." }.

The Git URL must be a valid HTTPS URL. Blackwall clones the repository with --depth 1, so no full history is needed. After installation, the module appears in the Modules tab where you can configure its settings, update it to the latest repository version, or uninstall it.

Security considerations Custom modules run inside the bot's process with full .NET capabilities. Only install modules from sources you trust. The collectible AssemblyLoadContext provides assembly isolation and hot-reloading but is not a security sandbox. Modules are built server-side during installation, so the build environment must have the .NET 10 SDK available.

Settings Key Convention

Keys without a prefix (e.g. maxEmojiCount) are user-configurable through the dashboard settings schema. Keys prefixed with __ (e.g. __action, __timeoutMinutes, __messageDeleteDays, __autoLockdown) are conventionally used for internal or action-related settings that may be managed separately or injected by the system. This is a convention only — all keys are stored in the same flat dictionary.
